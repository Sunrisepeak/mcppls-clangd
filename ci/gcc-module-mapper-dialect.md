# 0061: preserve GCC module mapper dialect when adjusting commands

The actual Qt CDB invokes GCC 16.1.0 with `-fmodules` and GCC mapper files listing named `std`, `std.compat` and `nlohmann.json` CMIs. It does not request Clang module maps. The existing command adjustment drops the unsupported mapper but retains `-fmodules`; Clang then adds automatic module-map discovery and builds `_Builtin_*` header modules that this GCC command never uses. Clang documentation explicitly describes this implication: [Clang modules command-line options](https://clang.llvm.org/docs/Modules.html#command-line-parameters). GCC describes separately built header units and mapper-controlled import translation: [GCC C++ modules](https://gcc.gnu.org/onlinedocs/gcc/C_002b_002b-Modules.html), [GCC module mapper](https://gcc.gnu.org/onlinedocs/gcc/C_002b_002b-Module-Mapper.html).

With patch0059, the producer's implicit PCMs remain alive. The Qt importer nevertheless loads `_Builtin_stddef` from consumer context `29X93P1OIGELY`, then named nlohmann's BMI imports another copy from producer context `15AZ85Y0DLKIT`. The resulting `module_file_conflict` prevents JSON completion. The full PCM info diff preserves the actual files: target/language/sysroot/resource/builtin inputs match; consumer has extra Qt include directories. Raw CDB command macros also differ by `QT_CORE_LIB`, `QT_GUI_LIB`, `QT_WIDGETS_LIB`; `CompilerInvocation::computeContextHash` hashes command macros, so these contexts naturally differ. Forcing one PCM into the other context would not establish general macro compatibility. The independent real compiler importer and compiler completion control succeeded without the Qt textual preamble, confirming the producer export itself is visible.

The fix uses the existing CommandMangler parser/unsupported-option adjustment boundary. It retains the original `-fmodules`, and adds `-fno-implicit-module-maps` only when the parsed raw arguments contained a nonempty GCC `-fmodule-mapper=` option and the effective driver has canonical GCC/g++ spelling (including target/versioned names). Classification happens after user config edits and before resolveDriver's alias-basename rewrite; a real g++ symlink to clang++ is excluded. No compiler execution or query-driver authorization is added. Generic `cc`/`c++`, Clang, no-mapper GCC commands and disabled modules are unchanged. Explicit Clang map/file/prebuilt/builtin or implicit-map options remain authoritative.

This is a narrow GCC dialect adaptation, not authenticated compiler-family detection or complete GCC mapper/header-unit support. Wrapper identities, unsupported mapper/header-unit paths and other compiler families remain outside its claim. The physical Qt GCC binary hash/version, original command bytes and actual mapper contents are retained in `raw-inputs.json`.

## Focused controls

`focused-final.log` exercises the positive dialect, nine command variants and a real cross-directory g++→clang++ symlink negative control. `builtin-control.json` retains the ordinary Clang `-fmodules` producer: it still creates a true `_Builtin_stddef` PCM and an independent second server reuses the same main/implicit dev/inode/size/full-mtime identities while completing `fn_bundle`.

`final-json-qualified.json` and `final-json-member.json` run the unchanged original Qt CDB, source and compiler flags. They preserve actual adjusted command logs (`-fmodules` remains), all raw LSP responses, and actual returned textEdit/snippet insertions. Each of the four cold/warm/edited requests in each context must return the expected semantic candidate, and every applied TU is compiled by the original CDB GCC command, including its mapper and `-fmodules`. Original disk source and CDB hashes are compared after the controls.

The earlier private-CDB experiment (`no-map-json-control.json`) established causality by adding only the translation flag, but is not the final unchanged-input proof. The matched patch0059 before controls retain JSON failure and the builtin identity-conflict diagnostic. The final correct semantic path still costs hundreds of milliseconds; this patch does not claim the 200/300 ms distribution gates, official-stock 50% improvement, full context matrix or native-platform runtime qualification. Further performance work must measure the now-correct named-module path.
