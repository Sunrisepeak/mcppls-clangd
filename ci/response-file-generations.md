# Immutable response-file CDB generations (0030 / UP-03)

0030 fixes JSON compilation database response-file generation correctness (UP-03 / W2).

Previously expandResponseFiles retained a live real filesystem: querying the same CDB pointer could produce different commands after an @response edit, while ProjectModulesCommandCache retained the first inventory for that pointer. The CDB owner therefore was not a reliable generation. Provider associations and module command inventories could remain stale even when direct command expansion changed.

The JSON loader now discovers response inputs using the supplied ThreadsafeFS view, including nested @response lookups, read errors, and absent files. A generation retains one byte/status/error snapshot per response path spelling, and a set of response paths for each source. Existing Tooling response expansion and command inference operate over this frozen, read-only VFS. The filesystem is released after discovery; no live filesystem access occurs when old generations expand their commands. Snapshot file buffers own their bytes. Raw UTF-16/BOM response bytes pass unchanged to the existing tokenizer. Recursion behavior and UID alias relationships are preserved.

Publication replays the complete captured input set against the loading filesystem. If bytes/status/error/alias relationships changed, the old generation remains published, the freshness timestamp does not advance, and CDB metadata is marked for rereading on the next query. All commands in a generation observe the same first-captured response bytes. This is validation of filesystem observations, not an atomic filesystem transaction; a writer may modify a file after any validation. Subsequent requests revalidate their applicable boundary.

Normal concrete-source queries validate their own response chain even within the existing freshness interval. Unknown/inferred sources conservatively validate all response inputs. At the existing general revalidation interval and at explicitly forced module inventory refresh, the distinct full response set is validated once before provider enumeration. Pure broadcast ownership probes skip response validation, avoiding O(N*R) reads during broadcasting. Neither a watcher nor a reliable external filesystem epoch is assumed. Validation reads exact contents even when size and the full mtime are identical.

A response-only change reparses retained raw JSON, publishes a new shared CDB owner, and thereby refreshes the retained module inventory and provider cache. Loading priorities, compile_flags.txt, generic plugins, ordinary JSON metadata policy, fallback/inference, config adjustment, and existing revalidation intervals remain in place. Original response generations still decline positive dependency-scan memo admission; this patch does not opt them in through pre-expansion provenance. Raw/failed response commands retain existing Tooling expansion semantics.

For N compile commands and R distinct response path spellings, a stable known-source query performs O(chain) filesystem probes and byte reads (with alias-map bookkeeping), a forced inventory boundary performs O(R) probes/reads, and generation rebuilding/discovery still tokenizes O(N) commands. Storage owns raw JSON, unique response bytes, and per-source path sets, rather than N copies of expanded response contents. Unknown/inferred queries can cost O(R). These are not hard RSS or compiler-admission bounds. Per-file config mangler work and independent bounded compiler admission remain separate W2 work.
