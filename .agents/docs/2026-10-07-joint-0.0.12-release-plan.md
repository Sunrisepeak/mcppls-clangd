# mcppls-clangd：联动 mcppls 0.0.12 的 release 契约

状态：2026-10-07，供 review，未实施。联合主方案位于兄弟仓库 [mcppls 0.0.12 joint release plan](../../../mcpp-language-server/.agents/docs/2026-10-07-0.0.12-joint-release-plan.md)，实测依据见 [维护版接入分析](../../../mcpp-language-server/.agents/docs/2026-10-07-maintained-clangd-0.0.12-plan.md)。这些是本地 review 链接；提交到各自 GitHub 后需改为对应不可变 commit 链接，不假称本地文档已发布。

## 1. 本仓交付边界

fork 修复 Clang/clangd 内部根因；mcppls 修复编译器画像、项目/CDB同步、调度/失效和打包。产品 workaround 是 containment，不自动代表引擎问题 fixed。默认启用引擎目标 `23.1.0-mcppls.1`，当前 `.0` 不具备发布资格。

当前阻断：0006 的成员补全污染；产品 inferred C7 模块导出更新180 s超时；raw import hang；const view patch 过宽且仍有假阳性；Windows真实corpus为空/未实现重放；平台构建与recipe不一致；现有bench缺语义断言；release未依赖全部验收。根因仍需逐个定位，不能直接按既有计划登记 steady。

## 3. 更正旧设计的强假设

- UP-25：index-only仅在被证明语义完备的上下文启用；关闭当前错误路径只是止损。BMI completion tables属于需要证明的设计候选，不能预先称“2–4周必然完成的durable fix”；Decl/ASTContext不能跨实例直接共享。
- UP-13：0007 `--crash-dumps-dir` 是取证能力，不是crash修复；产品须按明确opt-in启用并限制敏感dump，Windows PDB必须验证实际可符号化。
- UP-20：不要把未经证实的stack overflow当首要结论并统一增大栈；先取栈/reduce。Linux观察到的fan-out crash不能自动划成Windows问题。
- Windows CI：非空manifest必须真实执行；空corpus、找不到debugger、没有匹配PDB都不能作为绿色crash gate。
- workaround retirement：正确的`-c`编译命令和通用backoff/watchdog/隔离/bundle不移除；仅已证明对应raw canary通过的特定feature保护退休，原版引擎保留保护。
- 配方是可验证承诺：Linux20.04/glibc2.31、Windows CRT策略、macOS deployment target需要真实构建与最低OS运行验证；不可仅写recipe而runner仍用不同下限。

## 4. 发布共同门槛

联合主方案第4节给出待review预算：raw warm普通/限定名p95≤200 ms、模块成员p95≤300 ms；相同正确路径对约1 s原版至少改善50%；产品缓存p95≤50 ms；小fixture新导出生效≤5 s；已复现hang/crash为0；四平台≥2 h RC soak、fan-out≥1000次，资源/缓存有界。不得以丢符号、排除超时样本、重启成功抵消失败。

同时保持既定连续7次有效nightly soak+bench才steady；声明每个UP的fixed/mitigated/open及证据。基线与候选引擎、最终VSIX/CLI包SHA一起存档；未经联合产品安装验证的fork artifact不得直接成为0.0.12默认引擎。

执行顺序 G0证据/gate → G1正确/稳定 → G2真实性能与功能 → G3四平台产品化 → G4 RC review。当前只同步方案，不改patch/代码/workflow，不发布或删除生产保护。
